# Part A: Dataset Description Document

## A.1 Purpose
Describes the data used to train and evaluate the certificate authenticity assessment system: its sources, composition, labeling scheme, and known limitations, so that model results can be interpreted correctly and the dataset can be reproduced or extended.

## A.2 Data Sources

| Source Type | Description |
|---|---|
| Genuine certificates | Real or realistically reconstructed academic certificates (mark-sheets, degree certificates) collected with consent, or generated from institutional templates with plausible synthetic student data (no real personal data used without permission) |
| Manipulated certificates | Synthetically generated by programmatically altering genuine samples (see A.5) |
| Institutional templates (optional) | Blank/reference layouts supplied for template-matching evaluation |
| Public/reference datasets (optional) | Any publicly available document-forgery or ID-forgery datasets used for pretraining/benchmarking general tamper-detection features (e.g., general image-forensics datasets), clearly distinguished from the project's own certificate-specific data |

> **Note:** Since real student certificates carry personally identifiable information (PII), the dataset should either use anonymized/synthetic student data overlaid on real templates, or be collected with explicit institutional consent and anonymization before storage.

## A.3 Dataset Composition (Indicative)

| Split | Genuine | Manipulated | Total |
|---|---|---|---|
| Training | 70% of total | 70% of total | — |
| Validation | 15% of total | 15% of total | — |
| Test | 15% of total | 15% of total | — |

- Classes should be kept as balanced as possible (roughly 50/50 genuine vs. manipulated) to avoid biasing the classifier toward the majority class.
- Test set must contain manipulation types not overrepresented in training (to check generalization) plus common ones (to check baseline detection).

## A.4 Labeling Scheme

| Label Field | Description |
|---|---|
| `sample_id` | Unique identifier for the certificate image |
| `class` | `genuine` or `manipulated` |
| `manipulation_type` | One of: `name_altered`, `marks_altered`, `date_altered`, `cert_number_altered`, `signature_altered`, `seal_altered`, `multiple`, `none` |
| `manipulation_region` | Bounding box(es) of the altered region, where applicable |
| `source_institution_format` | Which template/format family the sample follows (for template-matching evaluation) |
| `image_quality` | `high` / `medium` / `low` (scan quality, resolution, lighting) — used to test robustness |

## A.5 Synthetic Manipulation Generation Methodology
To build a controlled, labeled dataset of manipulated samples from genuine ones:

1. **Field-level text editing** — programmatically replace name/marks/date/certificate-number text using image-editing scripts (font-matched or intentionally mismatched, to cover both subtle and obvious forgeries).
2. **Copy-paste/cloning** — duplicate a region (e.g., a digit or seal) elsewhere in the same or a different certificate.
3. **Signature/seal replacement** — swap or blend a signature/seal from a different sample.
4. **Compression/re-save artifacts** — resave locally edited regions at different JPEG quality levels to simulate real-world edit artifacts.
5. **Layout perturbation** — slightly shift/resize fields to simulate template mismatch.

Each generated sample retains a record of exactly which manipulation was applied and where, enabling both classification-level and region-level (localization) evaluation.

## A.6 Data Quality Considerations
- Include a range of scan qualities (phone photos, flatbed scans, screenshots) to reflect real-world submissions.
- Include multiple certificate format families (different universities/boards) if scope allows, to avoid overfitting to a single layout.
- Balance manipulation subtlety: include both obviously forged and carefully forged samples so evaluation reflects real detection difficulty.

## A.7 Privacy & Ethical Handling
- No real, non-consented personal data (names, register numbers) should be used in the training set; synthetic/anonymized identities are used instead.
- Dataset storage should be access-controlled and excluded from any public repository unless fully synthetic and anonymized.
- If any real institutional templates are used, they should be used only with permission and stripped of any real student data.

# Part B: Model Design Document

## B.1 Purpose
Describes the machine learning / deep learning approach used for the classification module (FR-ML-01 to FR-ML-04 in the SRD), including architecture, inputs/outputs, training methodology, and evaluation strategy.

## B.2 Problem Formulation
- **Task type:** Binary classification (genuine vs. manipulated), with an optional auxiliary task of manipulation-type classification and/or region localization.
- **Input:** Certificate image (preprocessed), plus optionally the structured feature set derived from OCR, text-consistency checks, and forensic analysis.
- **Output:** Probability of manipulation (0–1), and optionally per-manipulation-type probabilities and flagged region coordinates.

## B.3 Modeling Approach

### B.3.1 Feature Sources Feeding the Model
| Source | Feature Type |
|---|---|
| OCR module | Field confidence scores, text-length anomalies, character-level irregularities |
| Text-consistency module | Rule-violation flags (date logic, grade format, institution-name match) |
| Forensics module | Clone-detection score, font/spacing anomaly score, ELA compression score, layout-alignment deviation, seal/signature irregularity score |
| Template/record module | Template similarity score, record match/mismatch flag |
| Raw image | Pixel-level features for a CNN-based visual classifier |

### B.3.2 Candidate Architecture
A **two-branch (multimodal) model** is recommended:

1. **Visual branch (CNN):** A convolutional neural network (e.g., a ResNet/EfficientNet-style backbone, or a lightweight custom CNN given project scope) processes the certificate image (or image patches around suspicious regions) to learn visual tamper cues.
2. **Tabular branch:** A smaller feed-forward network (or gradient-boosted tree model, e.g., XGBoost/Random Forest, as a simpler alternative to a neural tabular branch) processes the engineered features from OCR/text-consistency/forensics/template modules.
3. **Fusion layer:** Concatenates outputs of both branches and passes through a final classification head to produce the manipulation probability.

> For an academic project timeline, a simpler baseline is also valid: start with the **tabular-only model** (Random Forest / XGBoost / Logistic Regression on engineered features) as a fast-to-train baseline, then add the CNN visual branch as a stretch goal if time permits. This staged approach also gives a clean ablation study (tabular-only vs. visual-only vs. fused) for the evaluation report.

### B.3.3 Model Inputs/Outputs Summary

| | Detail |
|---|---|
| Input (image branch) | Preprocessed certificate image, resized to fixed dimensions (e.g., 512×512) |
| Input (tabular branch) | Feature vector from OCR/consistency/forensics/template modules |
| Output | `manipulation_probability` (0–1), `predicted_class` (genuine/manipulated at chosen threshold), optionally `manipulation_type_probs`, `flagged_regions` |

### B.3.4 Explainability
- For the tabular branch: feature importance (e.g., SHAP values or built-in feature importance from tree-based models) to identify which signals drove the decision.
- For the visual branch (if implemented): Grad-CAM or similar saliency method to highlight image regions that influenced the prediction — these regions feed directly into the report's "flagged regions" visualization (FR-SCR-04).

## B.4 Training Methodology

| Aspect | Approach |
|---|---|
| Loss function | Binary cross-entropy (for the main classification head); optionally multi-task loss combining classification + region-localization loss |
| Optimizer | Adam (typical default; tune learning rate via validation performance) |
| Regularization | Dropout, data augmentation (rotation, brightness/contrast jitter, noise) on the image branch to improve robustness to scan-quality variation |
| Class imbalance handling | Balanced sampling / class weighting if genuine:manipulated ratio deviates from ~50/50 |
| Validation strategy | Hold-out validation set (see A.3) with early stopping based on validation F1-score |
| Hyperparameter tuning | Grid/random search over learning rate, batch size, dropout rate, tree depth (for tabular models) |

## B.5 Evaluation Strategy

| Metric | Purpose |
|---|---|
| Accuracy | Overall correctness (use cautiously if classes are imbalanced) |
| Precision | Of certificates flagged as manipulated, how many actually are — important to minimize false accusations |
| Recall | Of actually manipulated certificates, how many are caught — important for catching real forgeries |
| F1-score | Balance of precision and recall |
| Confusion Matrix | Full breakdown of true/false positives/negatives |
| Per-manipulation-type recall | Detection rate broken down by manipulation type (name/marks/date/signature/seal), to identify weak spots |
| Ablation comparison | Tabular-only vs. visual-only vs. fused-model performance, to justify the final architecture choice |

## B.6 Model Versioning & Deployment Notes
- Each trained model artifact is tagged with a version (e.g., `v1.0`, `v1.1`) and logged per prediction (as required by FR-ML-04 in the SRD) for auditability.
- Retraining triggers: new labeled data available, or systematic errors identified in production/testing feedback.
- Model artifacts stored separately from application code, loaded at inference time by the ML/DL Classifier Service (per the Architecture Document).

# Part C: Data Preprocessing Report

## C.1 Purpose
Documents the concrete preprocessing steps applied to raw certificate images before OCR, forensics, and ML analysis (implementing FR-PRE-01 to FR-PRE-05 from the SRD), along with the rationale and parameters used.

## C.2 Preprocessing Pipeline Steps

| Step | Technique | Purpose | Typical Parameters |
|---|---|---|---|
| 1. Format normalization | PDF → image rasterization (if input is PDF) | Ensure uniform image input for all downstream modules | 300 DPI rasterization recommended for text clarity |
| 2. Resizing | Aspect-ratio-preserving resize | Standardize input dimensions for OCR/CNN | Target long-edge size, e.g., 1600–2000 px for OCR; 512×512 for CNN branch |
| 3. Noise reduction | Gaussian blur / median filter / non-local means denoising | Reduce scan noise/graininess before OCR | Light denoising to avoid blurring fine text |
| 4. Contrast enhancement | Histogram equalization / CLAHE | Improve text-background separation for OCR and forensic analysis | CLAHE with clip limit tuned to avoid over-amplifying artifacts |
| 5. Normalization | Pixel value scaling (0–1 or standardized) | Prepare image for CNN input | Per-channel mean/std normalization |
| 6. Perspective/skew correction | Edge/contour detection + homography transform, or Hough-line-based deskewing | Correct angled photos/scans to a flat, front-facing view | Auto-detect certificate boundary; fallback to manual crop if detection fails |
| 7. Region segmentation (optional) | Layout detection to isolate text blocks, seal/signature regions | Improves both OCR field-mapping and forensic region-specific analysis | Rule-based or a lightweight layout-detection model |

## C.3 Preprocessing Pipeline Diagram

```
Raw Upload (image/PDF)

        ▼

        │
        ▼

```

## C.4 Handling Edge Cases

| Case | Handling Strategy |
|---|---|
| Very low-resolution scan | Flag as `image_quality: low`; proceed but lower confidence weighting on OCR/forensic outputs in final score fusion |
| Heavily skewed/rotated photo | Attempt auto-correction; if detection confidence is low, prompt user to re-upload or manually crop |
| Multi-page PDF | Process each page as a separate image; if the certificate spans multiple pages, allow user to indicate which page(s) to analyze |
| Certificate photographed with background clutter | Auto-detect and crop document boundary before further processing |
| Corrupted/unsupported file | Reject at ingestion stage (FR-ING-03) before reaching the preprocessing pipeline |

## C.5 Validation of Preprocessing Effectiveness
- Compare OCR field-extraction accuracy **before vs. after** each preprocessing step (ablation) to justify which steps meaningfully improve downstream accuracy.
- Visually spot-check a sample of preprocessed images to confirm no critical information (e.g., certificate number digits) is lost or distorted by aggressive denoising/contrast steps.
